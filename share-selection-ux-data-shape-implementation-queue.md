# Implementation Queue — Sprint 1 Execution Step 4: Share Selection UX and Data Shape

## Назначение

Этот документ переводит **Execution Step 4 — Share Selection UX and Data Shape** в конкретную очередь реализации. Это самый чувствительный шаг Sprint 1, потому что именно здесь пользовательский сценарий перестаёт быть просто narrative-путём и превращается в конкретное действие: выбор доли участия в животном. Цель шага — сделать так, чтобы интерфейс оперировал **понятными пользовательскими долями**, а не внутренней технической slot-моделью, и при этом оставался устойчивым к неполным или нестабильным данным [1] [2] [3].

Execution Step 4 должен происходить после стабилизации Home, карточек и decision page профиля. До этого момента пользователь уже понимает идею продукта, видит единый язык карточек и получает ясный профиль животного как страницу решения. Теперь нужно устранить последний источник трения: **сделать выбор доли прозрачным, линейным и предсказуемым** [1] [2].

## Целевой результат шага

После завершения этого шага пользователь не должен сталкиваться с техническими сущностями, конфликтующими процентами, `NaN`, непонятной стоимостью шага или двусмысленным следующим действием. Экран выбора доли должен говорить простым языком: сколько уже занято, какие доли ещё доступны, сколько стоит выбранная доля и что произойдёт дальше [1] [2].

| Что должно измениться | Как выглядит успех |
|---|---|
| **UI-язык выбора доли** | Пользователь видит `10%`, `20%`, `30%` и т. п., а не slots, fragments или внутренние квоты |
| **Экономика выбора** | Стоимость доли считается прозрачно и не меняет смысл между страницами |
| **Состояния доступности** | Доступные и занятые доли отображаются без конфликтов и пустых значений |
| **Следующий шаг** | После выбора доли пользователь понимает, что именно произойдёт дальше |
| **Устойчивость UI** | Неполные данные больше не ломают компонент выбора и не создают `undefined.length` / `NaN` |

## Canonical User-Facing Share Model

Ключевая задача этого шага — ввести **каноническую пользовательскую модель долей**, поверх которой уже может жить любая внутренняя server/admin логика. Внутренние сущности могут остаться на месте, но UI должен видеть стабильный shape [1] [3].

| Поле | Роль в UI | Обязательность |
|---|---|---|
| `availableSharePercents` | Какие доли можно выбрать прямо сейчас | Обязательно |
| `occupiedSharePercent` | Какой процент уже занят | Обязательно |
| `selectedSharePercent` | Что выбрал пользователь | Обязательно для локального UI-state |
| `shareUnitPercent` | Базовый шаг доли | Обязательно |
| `shareUnitPriceMinor` / `baseSharePrice` | Цена одного шага | Обязательно |
| `selectedSharePriceMinor` | Стоимость текущего выбора | Желательно, можно derive |
| `availabilityLabel` | Человеческое объяснение текущей доступности | Желательно |
| `nextActionLabel` | Что произойдёт после выбора | Обязательно |

> Важно: Sprint 1 не требует полной замены внутренней модели хранения долей. Он требует **тонкого адаптера** между внутренней моделью и стабильным UI-shape, чтобы пользовательский интерфейс перестал зависеть от хрупких вычислений в JSX [1] [2].

## Implementation Queue

### Queue Item 1 — Провести inventory всех share-related surface-слоёв

Сначала нужно определить, где именно в продукте уже существует логика выбора доли, отображения доступности и вычисления стоимости. Это не только профиль животного, но и возможные вспомогательные блоки, admin-страницы, helper-функции и серверные мапперы. Без этой карты нельзя безопасно отделить пользовательскую модель от внутренней slot-модели.

| Что сделать | Как выполнить | Файлы |
|---|---|---|
| Найти все share UI blocks | Проверить профиль животного, возможные selection panels, CTA-блоки и preview states | профильные страницы в `client/src/pages/` |
| Найти все вычисления процентов и цены | Поиск по `availableSharePercents`, `shareUnitPercent`, `shareUnitPriceMinor`, `occupiedSharePercent`, `formatPrice` | client/server/helpers |
| Найти server-side источники shape | Проверить `server/db.ts`, `server/routers.ts`, возможные мапперы | `server/db.ts`, `server/routers.ts` |

### Queue Item 2 — Зафиксировать canonical UI shape как отдельный контракт

Следующий шаг — явно описать, какой именно shape должен получать пользовательский интерфейс. Пока этого нет, UI будет продолжать вычислять недостающие поля самостоятельно, что и рождает `NaN`, пустые проценты и расхождения между страницами. Нужно ввести один тонкий contract-layer, даже если источник данных остаётся прежним [1] [2].

| Что сделать | Что должно получиться |
|---|---|
| Описать UI-share type | Один тип для профиля и связанных selection-компонентов |
| Зафиксировать обязательные поля | `availableSharePercents`, `occupiedSharePercent`, `shareUnitPercent`, `shareUnitPriceMinor`, `nextActionLabel` |
| Установить safe defaults | Пустой массив, `0`, fallback-labels, безопасная цена |

**Вероятные файлы:** новый shared/client helper, профильный UI-helper, возможно types рядом с карточечным contract-layer.

### Queue Item 3 — Вынести нормализацию share shape в один adapter layer

После определения контракта нужно создать единый нормализатор, который преобразует текущую модель сервера в stable UI-shape. Это может быть либо клиентский adapter, либо тонкий серверный mapper. Для Sprint 1 предпочтительно двигаться к более чистому shape с сервера, но если это увеличивает риск, допустим промежуточный adapter layer на границе UI [1] [3].

| Что сделать | Критерий успеха |
|---|---|
| Создать normalizer/adapter | Все share-компоненты получают один безопасный shape |
| Убрать ad hoc вычисления из JSX | Компоненты рендерят готовые данные, а не считают их на месте |
| Защитить массивы и проценты | Нет `.length` у `undefined`, нет `NaN`, нет пустых ключевых полей |

### Queue Item 4 — Пересобрать UX выбора доли как линейный decision step

Даже с хорошими данными UX может оставаться запутанным. Нужно проверить, как именно пользователь выбирает долю: понимает ли он доступные опции, видит ли изменение стоимости, понимает ли границы выбора и получает ли ясный feedback после клика. Выбор доли должен ощущаться как короткий линейный decision step, а не как разгадывание внутренней схемы распределения [1] [2].

| Что должен видеть пользователь | Почему это важно |
|---|---|
| Сколько уже занято | Создаёт контекст scarcity и прозрачности |
| Какие опции доступны сейчас | Убирает двусмысленность выбора |
| Сколько стоит выбранная доля | Делает decision concrete |
| Что произойдёт после выбора | Снижает тревожность перед следующим шагом |

| Что сделать | Решение |
|---|---|
| Проверить способ отображения опций | Кнопки/segmented selection/tiles должны быть однозначными |
| Показать selected state явно | Пользователь должен видеть текущий выбор без сомнений |
| Показать стоимость рядом с выбором | Цена должна обновляться прозрачно |
| Уточнить next-step copy | Например: «Продолжить к оформлению участия» или иной честный placeholder-flow |

### Queue Item 5 — Согласовать share UX с карточками и profile language

Execution Step 4 не должен жить отдельно от всего conversion spine. Терминология и economics, которые видны в карточках и профиле, должны совпадать с блоком выбора доли. Если карточка обещает «минимальная доля 10%», а на selection step это превращается в иную единицу, пользователь теряет доверие [1] [2].

| Что сделать | Критерий |
|---|---|
| Сверить labels и helper-copy | Термины доли, доступности и цены совпадают во всём funnel |
| Сверить share metrics | Значения на карточке/профиле и в selection UI не конфликтуют |
| Сверить CTA semantics | Следующее действие называется одинаково и честно |

### Queue Item 6 — Решить, где должна жить основная нормализация: server-first или client-adapter first

На этом шаге важно принять практичное архитектурное решение. В долгую нормализация должна уходить ближе к серверу, чтобы UI получал чистый продуктовый shape. Но в Sprint 1 приоритет — надёжно закрыть vertical slice. Поэтому нужно сознательно выбрать, где будет жить основная адаптация сейчас и как это не создаст технический долг, который помешает Phase C.

| Вариант | Когда уместен |
|---|---|
| **Client adapter first** | Если текущий серверный shape нестабилен, а нужно быстро стабилизировать UI |
| **Server mapper first** | Если можно безопасно изменить `adminAnimals.list` / animal profile payload без цепочки регрессий |
| **Hybrid** | Сервер выдаёт базовую нормализацию, UI добавляет только display-safe defaults |

> Рекомендация для Sprint 1: выбрать **hybrid**. Сервер должен отдавать более продуктовый shape, а UI — добавлять только безопасные display-fallbacks. Это снижает риск будущего расхождения между публичным и административным слоями [2] [3].

### Queue Item 7 — Закрепить regression safety для share model

После стабилизации контракта и UX нужно обязательно закрепить его тестами. Иначе блок выбора доли снова станет точкой регрессий при любом изменении профиля животного, карточек или admin-данных. Нужно тестировать не только happy path, но и неполные/пограничные shape-сценарии [1] [3].

| Что сделать | Тип проверки |
|---|---|
| Проверить normalizer на пустых и неполных полях | Vitest helper test |
| Проверить derive цены и selected state | Vitest helper test |
| Проверить отсутствие runtime-ошибок в selection UI | Smoke/profile render test |
| Проверить user-facing labels | Smoke/manual preview |

## File-Level Implementation Order

| Очередь | Файл | Первое действие |
|---|---|---|
| **1** | профильные страницы и share UI blocks | Зафиксировать текущие share surface-слои |
| **2** | `server/db.ts` / `server/routers.ts` | Найти источник текущего share shape |
| **3** | новый share adapter/helper | Описать canonical UI-share contract |
| **4** | профильный UI | Перевести selection block на adapter shape |
| **5** | дополнительные UI blocks | Убрать локальные вычисления цены и процентов |
| **6** | тестовые файлы | Добавить helper tests и smoke coverage |

## Suggested Definition of Done for Step 4

| Done condition | Что значит на практике |
|---|---|
| UI показывает понятные доли | Пользователь видит проценты, а не внутренние slots |
| Экономика прозрачна | Цена выбора и базовый шаг понятны |
| Доступность корректна | Нет конфликтов между занятой и свободной долей |
| Next step ясен | После выбора пользователь понимает, что произойдёт |
| Неполные данные не ломают UI | Нет `NaN`, `undefined.length`, пустых процентов |
| Regression coverage добавлено | Есть helper tests и preview/smoke validation |

## Immediate Next Action

Следующее практическое действие после этой очереди — **сделать inventory текущих share-related вычислений и определить минимальный canonical UI-share contract**, прежде чем менять рендер или тексты в профиле. Без этого велик риск повторно зашить защитные fallback-вычисления прямо в JSX и снова получить хрупкую модель [1] [3].
