# Product Operating System — Sher Kozu

## Назначение

Этот документ задаёт рабочую систему принятия решений для проекта Sher Kozu. Его цель — сделать так, чтобы разработка двигалась вокруг **реального core flow продукта**, а не распадалась на случайные багфиксы, локальные хотелки и технический шум.

## Core Flow

Текущий базовый пользовательский сценарий выглядит так: пользователь приходит на главную страницу, понимает идею персонального фермерства, переходит в галерею животных, выбирает конкретное животное, изучает его профиль, понимает механику шэринга и затем попадает в опыт владения — трекер, клуб и личный контур. Эта логика согласуется с дизайн-направлением проекта и с ранее сохранёнными продуктовыми выводами [1] [2].

## Правило продуктового приоритета

Любая новая задача должна сначала отвечать на вопрос: **усиливает ли она один из четырёх ключевых контуров** — acquisition, conversion to share, ownership experience, farm operations. Если задача не усиливает ни один из этих контуров, она не должна попадать в верх списка работ.

| Контур | Вопрос для приоритизации | Примеры допустимых задач |
|---|---|---|
| **Acquisition** | Помогает ли задача лучше объяснить продукт и привести пользователя к выбору животного? | Главная, narrative-блоки, галерея, trust-секции |
| **Conversion to Share** | Повышает ли задача ясность и надёжность выбора доли? | Профиль животного, цена, доля, CTA, статусы |
| **Ownership Experience** | Делает ли задача владение живым и ценным после выбора животного? | Dashboard, Club Feed, Product Tracker, profile routing |
| **Farm Operations** | Помогает ли задача ферме поддерживать основной пользовательский сценарий? | Admin Animals, CRM, club operations, monitoring |

## Правило вертикальных срезов

Разработка должна идти вертикальными срезами, а не россыпью несвязанных изменений. Это означает, что спринт берёт один продуктовый путь и доводит его до устойчивого состояния через интерфейс, сервер, данные и тесты. Например, корректный спринт — это «усилить путь выбора доли у животного», а не отдельные разрозненные правки в Home, админке и клубе без общего результата.

## Правило документации

В проекте должны жить только три активных управляющих документа. `todo.md` хранит текущие исполнимые задачи, `roadmap.md` хранит среднесрочные фазы и приоритеты, а этот документ фиксирует правила принятия решений. Все остальные заметки считаются рабочими артефактами и не должны использоваться как главный источник правды.

## Правило `todo.md`

`todo.md` должен содержать только такие задачи, которые можно реально брать в ближайшие итерации. Завершённые исторические хвосты допустимы как архив, но активная зона документа должна быть короткой, сгруппированной по фазам и ориентированной на следующие 1–2 спринта. Если задача не выглядит важной в ближайшем core flow, она должна быть либо опущена ниже, либо перенесена в backlog внутри roadmap, а не мешать рабочему списку.

## Правило roadmap

Roadmap не должен перечислять каждую мелкую задачу. Его функция — держать направление. Для Sher Kozu это означает четыре последовательные фазы: stabilise conversion spine, build ownership experience, strengthen farm operations, finish trust and publish readiness. Если новая работа не укладывается в одну из фаз, значит её приоритет нужно пересмотреть.

## Правило багфиксов

Не каждый баг является приоритетным. Баги уровня Home, Gallery, Animal Profile, Share Flow, Dashboard owner journey и admin-поддержки животных — это bugs in core flow и они должны подниматься наверх. Баги во вторичных или экспериментальных зонах должны исправляться тогда, когда не размывают основной продуктовый контур.

## Правило done

Задача считается по-настоящему завершённой только тогда, когда выполнены четыре условия: пользовательский сценарий работает, данные согласованы, smoke/vitest покрытие обновлено, а запись в `todo.md` и roadmap не противоречит текущему состоянию проекта. Это нужно, чтобы не копить «полузакрытые» изменения.

## Рекомендуемый цикл на каждую итерацию

| Шаг | Смысл |
|---|---|
| Определить контур | Понять, какой именно продуктовый контур усиливаем сейчас |
| Выбрать vertical slice | Взять 3–5 связанных задач, ведущих к одному заметному результату |
| Довести код и данные | Закрыть UI, сервер, маршруты и тесты в одном контуре |
| Обновить документы | Поддержать `todo.md`, `roadmap.md` и этот документ в актуальном состоянии |
| Зафиксировать checkpoint | Сохранить понятную контрольную точку после завершения среза |

## Практическое следствие для текущего этапа

На текущем этапе проекту не нужен ещё один широкий список хотелок. Ему нужна **фокусировка**. Следующий сильный ход — собрать короткий рабочий backlog вокруг пути `Home → Gallery → Animal Profile → Share`, затем вторым блоком довести `Dashboard / Product Tracker / Club` до состояния настоящего ownership experience, и только после этого системно возвращаться к сложной административной архитектуре.
