# Архитектура полной перестройки Зои

## 1. Текущее состояние

Сейчас `nutriProfiles` хранит одну необязательно заполненную запись на пользователя: цели, аллергии, ограничения, членов семьи и предпочтительные продукты. В таблице нет имени профиля, пола, даты рождения, роста, веса, активности, признака основного профиля, состояния заполнения и даты подтверждения. Уникальное ограничение на `userId` отсутствует, но сервер всегда читает только первую запись и обновляет все строки пользователя.

Оба чат-пути — tRPC и SSE — отдельно собирают одинаковый контекст. Они загружают одиночный профиль, owner-контекст и RAG, затем либо возвращают детерминированный шаблон меню, либо вызывают внешний AI. Web-чат и Telegram Mini App не имеют выбора профиля, анкеты или подтверждения актуальности данных.

Owner-контекст содержит полезные live-данные: активные владения, животных, анализы молока, производственные метрики, технологически возможные продукты, подтверждённые планы и доставки. Однако текущий prompt передаёт часть данных как `any[]` и не отделяет возможный ассортимент от фактической продукции клиента достаточно строго.

Текущий статический prompt содержит неподтверждённые и потенциально опасные обобщения. В новой архитектуре медицинские и продуктовые утверждения должны поступать из проверенного RAG или из явно маркированных справочных таблиц, а не из большого статического блока.

## 2. Целевая доменная модель

Один аккаунт имеет один основной и произвольное число дополнительных профилей питания. Профиль принадлежит только пользователю и содержит:

- имя профиля и отношение к владельцу аккаунта;
- пол, дату рождения, рост и вес;
- цели и уровень активности;
- аллергии, ограничения и предпочтения;
- явное подтверждение отсутствия аллергий и ограничений;
- состояние анкеты (`draft` или `complete`), дату подтверждения и дату последней проверки;
- признак основного профиля и мягкое архивирование.

Чат-сессия может быть связана с конкретным профилем. Если профиль не передан, сервер выбирает основной активный профиль. Клиентский `profileId` является только пожеланием: сервер обязательно проверяет принадлежность профиля текущему пользователю.

## 3. Состояния персонального диалога

Состояние определяется сервером по данным, а не по совпадению отдельных фраз:

| Состояние | Действие |
|---|---|
| Гость | Общая информация; персональная рекомендация предлагает авторизацию |
| Нет профиля | Предложить анкету или продолжить с общим вопросом |
| Профиль `draft` | Показать недостающие обязательные поля |
| Профиль заполнен | Показать компактное подтверждение и действия использования/изменения/выбора |
| Контекст подтверждён | Собрать персональный, продуктовый и научный контекст |
| Нужны данные запроса | Задать минимальное уточнение, сохранив профиль и задачу сессии |
| Данных достаточно | Выполнить расчёты, вызвать AI и проверить ответ |

## 4. Уровни доверия

1. **Факты клиента** — подтверждённые поля выбранного профиля.
2. **Факты фермы** — активный продуктовый план, доставки, анализы и live-данные.
3. **Проверенные знания** — активные RAG-записи со статусом и источником.
4. **Справочные оценки** — типовые КБЖУ аналогов с обязательной маркировкой.

Конфликтующие, архивные и неподтверждённые медицинские записи не попадают в контекст рекомендации.

## 5. Оркестратор

Один серверный orchestrator используется tRPC и SSE. Он:

1. определяет намерение;
2. выбирает и проверяет профиль;
3. вычисляет недостающие поля;
4. собирает подтверждённые продукты и варианты;
5. получает релевантные RAG-записи;
6. выполняет детерминированные расчёты;
7. формирует структурированный AI-контекст;
8. получает структурированный результат модели;
9. проверяет продукты, запреты, арифметику, источники и медицинские формулировки;
10. рендерит проверенный ответ с основным вариантом и 1–2 заменами.

Если модель недоступна или результат не проходит проверку, система не показывает непроверенный текст. Она возвращает короткое объяснение и сохраняет собранный контекст для повторной попытки.

## 6. Миграционная стратегия

Существующая запись каждого пользователя преобразуется в основной профиль. Старые поля сохраняются. Новые обязательные поля остаются nullable до заполнения анкеты, а `onboardingStatus` устанавливается в `draft`. Это позволяет выпустить миграцию без потери существующих данных.

Новая схема должна добавить связь `nutritionProfileId` к чат-сессии и сохранённым планам питания. Старые записи остаются читаемыми с `NULL`, а сервер разрешает их через основной профиль пользователя.

## 7. Границы первой реализации

Первая реализация включает web-чат, плавающий web-чат и Telegram Mini App; все они используют один профильный API и один orchestrator. Она не меняет production-данные напрямую: изменения схемы сначала применяются и проверяются в dev-базе, затем передаются в чекпоинте для явной публикации.

## 8. Точная схема профиля

Таблица `nutriProfiles` расширяется без удаления старых колонок. Новые поля:

| Поле | Назначение |
|---|---|
| `profileName` | Отображаемое имя профиля |
| `relationship` | `self`, `spouse`, `child`, `family`, `other` |
| `gender` | `male` или `female`; nullable до заполнения анкеты |
| `birthDate` | Дата рождения без времени |
| `heightCm`, `weightKg` | Актуальные антропометрические данные |
| `activityLevel` | `low`, `light`, `moderate`, `high`, `very_high` |
| `activityDetails` | Виды, частота и продолжительность нагрузок |
| `dislikedProducts` | Нежелательные продукты |
| `mealPreferences` | Число приёмов пищи и режим |
| `medicalNotes` | Добровольные пояснения пользователя |
| `noAllergiesConfirmed` | Явное подтверждение отсутствия аллергий |
| `noRestrictionsConfirmed` | Явное подтверждение отсутствия ограничений |
| `isPrimary` | Основной профиль аккаунта |
| `onboardingStatus` | `draft` или `complete` |
| `confirmedAt`, `lastReviewedAt` | Подтверждение и актуальность данных |
| `archivedAt` | Мягкое удаление дополнительного профиля |

Обязательная полнота профиля определяется серверной функцией, а не `NOT NULL`: имя, отношение, пол, дата рождения, рост, вес, хотя бы одна цель, активность, а также либо заполненный список аллергий/ограничений, либо явное подтверждение их отсутствия. Такой подход сохраняет черновик анкеты и не ломает миграцию старых записей.

`nutriSessions` получает `profileId`, `profileConfirmedAt` и JSON-поле `contextState`. В `contextState` хранятся только параметры текущей задачи: тип запроса, ожидаемое уточнение и уже подтверждённые расчётные значения. Медицинские и антропометрические факты остаются в профиле, а не дублируются в истории диалога.

`nutriMealPlans` получает `profileId`, чтобы сохранённая рекомендация всегда была связана с человеком, для которого она создана.

## 9. Серверный API профилей

| Процедура | Поведение |
|---|---|
| `profiles.list` | Активные профили текущего пользователя, основной первым |
| `profiles.getActive` | Профиль сессии либо основной профиль |
| `profiles.create` | Создание основного профиля при отсутствии или дополнительного профиля |
| `profiles.update` | Частичное сохранение анкеты с пересчётом полноты |
| `profiles.setPrimary` | Атомарно снимает предыдущий основной статус и назначает новый |
| `profiles.archive` | Мягко удаляет только дополнительный профиль |
| `profiles.confirm` | Обновляет дату подтверждения и переводит заполненный черновик в `complete` |
| `profiles.getRequirements` | Возвращает недостающие обязательные поля и необходимость повторной проверки |

Старые `getProfile` и `updateProfile` временно остаются совместимыми: они читают/обновляют основной профиль через новый сервис.

## 10. Контракт чат-запроса

Web/SSE и Telegram/tRPC передают опциональный `profileId` и действие подтверждения профиля. Сервер никогда не доверяет идентификатору без проверки владельца. Ответ включает структурированную метаинформацию: выбранный профиль, полноту анкеты, недостающие поля, необходимость подтверждения и доступные действия. Текст AI не используется для управления интерфейсом профиля.

## 11. Валидация рекомендации

Внешняя модель возвращает JSON по строгой схеме: краткое резюме, использованные факты профиля, меню, КБЖУ, выбранные продукты фермы, замены, предупреждения, ссылки на evidence IDs и пояснение оценочных значений. Сервер отклоняет результат, если:

- упомянут продукт вне разрешённого набора;
- нарушена аллергия или жёсткое ограничение;
- сумма КБЖУ/граммов выходит за заданный допуск;
- использован конфликтующий или неразрешённый источник;
- справочные значения представлены как лабораторные;
- присутствует диагноз, лечение или небезопасное обещание.

После проверки сервер формирует Markdown. Это исключает зависимость интерфейса от свободного текста модели и обеспечивает одинаковый результат в tRPC и SSE.
