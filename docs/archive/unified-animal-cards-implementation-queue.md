# Implementation Queue — Sprint 1 Execution Step 2: Unified Animal Cards

## Назначение

Этот документ переводит **Execution Step 2 — Unified Animal Cards** в конкретную очередь реализации. Его задача — устранить расхождения между карточками животных на главной странице, в каталоге `/animals` и на переходах к профилю, чтобы пользователь везде видел один и тот же продуктовый объект: **животное как точку выбора доли и начала отношений с фермой** [1] [2] [3] [4].

Сейчас карточки уже содержат часть нужной информации, особенно в `AnimalsCatalog.tsx`: статус отношений, цену, занятость, свободную долю и переход в профиль. Но для Sprint 1 важно не просто «улучшить карточки», а зафиксировать **единый контракт карточки** и затем заставить все surface-слои использовать именно его [1] [4].

## Целевой результат шага

После завершения этого шага пользователь должен получать одинаковый смысловой сигнал о животном на всех входных поверхностях. Карточка не должна менять логику интерпретации в зависимости от страницы. Если животное «можно шерить» в каталоге, та же смысловая рамка, та же ключевая метрика и тот же тип CTA должны сохраняться на главной и при переходе к профилю [1] [2].

| Что должно стать единым | Как выглядит успех |
|---|---|
| **Статус карточки** | Один словарь статусов и один визуальный паттерн для `в отношениях`, `на выданье`, `можно шерить` |
| **Ключевые метрики** | Цена, занятость, свободная доля и минимальный шаг отображаются одинаково |
| **CTA** | Везде один смысл: открыть профиль и перейти к выбору доли |
| **Тональность карточки** | Карточка говорит о персональном фермерстве, а не о каталожной SKU-единице |
| **Fallback-данные** | Неполные данные не ломают UI и не создают `NaN`, пустые проценты или конфликтующие подписи |

## Canonical Card Contract

Прежде чем менять UI, нужно зафиксировать **канонический контракт карточки**, который затем может использоваться в Home, `/animals` и в подготовке входа к профилю [2] [3]. Я рекомендую считать обязательными следующие поля.

| Поле | Назначение | Обязательность для UI |
|---|---|---|
| `id`, `slug`, `name`, `species` | Идентичность и маршрутизация | Обязательно |
| `coverImageUrl` | Основной визуальный образ | Обязательно, с fallback-state |
| `breed` | Породный или характерологический descriptor | Обязательно, с безопасным fallback |
| `status` / derived relationship state | Главная интерпретация карточки | Обязательно |
| `fullPriceMinor` | Полная стоимость животного | Обязательно |
| `ownedPercent` | Уже занятая доля | Обязательно |
| `availablePercent` | Свободная доля | Обязательно |
| `shareUnitPercent` | Минимальный шаг участия | Обязательно |
| `shareUnitPriceMinor` | Стоимость минимального шага | Обязательно |
| `availableSharePercents` | Доступные конфигурации выбора | Желательно, но с безопасным fallback |
| `shortDescription` | Короткий эмоционально-функциональный descriptor | Обязательно |
| `isFeatured` | Усиление приоритета в некоторых surface-слоях | Опционально |
| `occupiedUntil` | Усиление объяснения для статуса `в отношениях` | Условно обязательно |

> Важно: этот шаг не требует превращать все карточки в один физический компонент немедленно. Сначала нужно зафиксировать **единый shape**, затем привести визуальные поверхности к нему, и только после этого — при желании — выделить общий компонент [1] [2].

## Implementation Queue

### Queue Item 1 — Сделать inventory всех карточечных surface-слоёв

Сначала нужно определить, где именно карточка животного уже существует или имитируется. В проекте это как минимум `Home.tsx`, `AnimalsCatalog.tsx`, а также возможные preview-блоки или переходные элементы в профиле животного. Без этой карты легко унифицировать только каталог и упустить главную страницу.

| Что сделать | Как выполнить | Файлы |
|---|---|---|
| Найти все карточечные реализации | Просмотреть `Home.tsx`, `AnimalsCatalog.tsx`, а затем grep/search по `shortDescription`, `availablePercent`, `shareUnitPercent`, `featuredAnimal` | `client/src/pages/Home.tsx`, `client/src/pages/AnimalsCatalog.tsx`, смежные UI-файлы |
| Зафиксировать различия | Отметить, какие поля и CTA показываются на каждой поверхности | Рабочая заметка или прямо implementation doc |
| Выделить primary и secondary surface | Primary: Home gallery, `/animals`; Secondary: hero-preview, featured blocks, related animals | Те же файлы |

### Queue Item 2 — Вынести общий derived-state словарь статусов

Сейчас в каталоге уже есть логика `getRelationshipStatus`. Это хороший старт, но для Unified Animal Cards её нужно считать **общим карточным правилом**, а не частной функцией страницы каталога. Следующий шаг — определить, где должен жить единый derived helper для статуса, helper-текста, label и style-token.

| Что сделать | Решение |
|---|---|
| Определить canonical helper для статусов | Вынести `getRelationshipStatus` и, при необходимости, `formatCurrency`/`formatOccupiedUntil` в общий UI-helper уровень |
| Проверить совместимость с Home | Home должен использовать тот же словарь, а не собственные подписи статуса |
| Убрать дрейф копирайта | В разных карточках не должно быть разных названий одного и того же статуса |

**Вероятные файлы:** `client/src/pages/AnimalsCatalog.tsx`, возможный новый helper-файл в `client/src/lib` или `client/src/pages`-adjacent utilities, затем `client/src/pages/Home.tsx`.

### Queue Item 3 — Нормализовать data-shape для карточек на входе

Карточки уже страдали от неполных полей и `NaN` в админке; тот же риск есть и на публичных surface-слоях. Поэтому до выравнивания визуала нужно ввести единый слой нормализации карточечных данных. Карточка должна получать **безопасный публичный UI-shape**, даже если API частично вернул `null`, `undefined` или пропущенные share-поля [4].

| Что сделать | Что должно быть в результате |
|---|---|
| Создать нормализатор карточки | Функция возвращает полный безопасный объект для UI-рендера |
| Установить fallback-значения | `0%`, пустой массив, fallback-breed, fallback-price formatting without `NaN` |
| Применить нормализацию во всех surface-слоях | И Home, и каталог работают не с сырой моделью API, а с публичным card-shape |
| Зафиксировать shape в типах | Тип карточки не должен плавать между страницами |

**Вероятные файлы:** `client/src/pages/Home.tsx`, `client/src/pages/AnimalsCatalog.tsx`, возможно новый `client/src/lib/animalCard.ts` или аналогичный helper.

### Queue Item 4 — Согласовать информационную иерархию карточки

После унификации data-shape нужно выровнять то, **в каком порядке** карточка сообщает смысл. Пользователь сначала должен понять статус и имя животного, затем экономику выбора, затем следующий шаг. Если на одной странице карточка начинается с эмоции, а на другой — с цифр, конверсионный spine распадается.

| Информационный слой | Рекомендуемый порядок |
|---|---|
| **1. Identity** | species badge, имя, breed/descriptor |
| **2. Relationship state** | главный статус и helper-copy |
| **3. Share economics** | полная цена, занятость, свободная доля, минимальный шаг |
| **4. Availability options** | доступные проценты или конфигурации выбора |
| **5. Narrative descriptor** | короткий `shortDescription` |
| **6. CTA** | открыть профиль и выбрать долю |

| Что сделать | Критерий успеха |
|---|---|
| Сравнить порядок блоков в Home и `/animals` | Он должен быть согласован, даже если плотность контента разная |
| Убрать визуальные конфликты | Одни и те же данные не должны быть то headline, то secondary-note |
| Проверить featured-state | `Профиль недели` не должен ломать общую иерархию карточки |

### Queue Item 5 — Привести CTA к одному контракту

Карточка должна везде обещать одно и то же действие: переход к полному профилю животного и выбору доли. Если в одном месте CTA звучит как исследование профиля, а в другом — как покупка, пользователь видит два разных продукта.

| Что сделать | Решение |
|---|---|
| Определить единый CTA-copy | Базовый шаблон: «Открыть профиль и выбрать долю» |
| Проверить hero/featured-card CTA | Даже упрощённая карточка на Home должна вести в тот же сценарий |
| Согласовать click-surface | Везде кликабельна либо вся карточка, либо явно выделенный footer-CTA, но логика едина |

### Queue Item 6 — Определить уровень реюза: общий компонент или общий layout contract

На этом шаге нельзя автоматически тащить проект в premature abstraction. Нужно решить, что выгоднее сейчас: быстро унифицировать карточки общим helper-contract и стилевым паттерном или уже вынести их в один компонент `AnimalCard`. Для Sprint 1 я рекомендую сначала выровнять contract и markup-pattern, а затем, если расхождения исчезли, вынести реальный общий компонент.

| Вариант | Когда выбирать |
|---|---|
| **Общий helper + частные шаблоны** | Если Home и каталог отличаются по плотности, но должны говорить одним языком |
| **Общий `AnimalCard` component** | Если структура после выравнивания становится практически одинаковой |

> Рекомендация для Sprint 1: сначала добиться смыслового и data-единства, потом принимать решение о component extraction. Это снижает риск преждевременного абстрагирования [1] [4].

### Queue Item 7 — Зафиксировать smoke/vitest protection для unified contract

Unified Animal Cards — это не просто визуальная задача. Её нужно закрепить регрессионно. Минимум: тест на безопасную нормализацию карточечного shape, тест на derived relationship status и smoke-проверка присутствия ключевых card markers на Home и в `/animals` [1] [4].

| Что сделать | Тип проверки |
|---|---|
| Проверить normalizer с неполными данными | Vitest helper test |
| Проверить derived relationship labels | Vitest helper test |
| Проверить ключевые markers карточки в каталоге | Smoke/page visuals test |
| Проверить карточечный entry-point на Home | Smoke/page visuals test |

## Suggested Definition of Done for Step 2

Execution Step 2 можно считать завершённым только если карточка стала единым публичным интерфейсом животного на всех входных поверхностях [1] [2].

| Done condition | Что значит на практике |
|---|---|
| Статусы унифицированы | Один статус-словарь и один тип helper-copy |
| Метрики унифицированы | Цена, занятость, свободная доля и шаг показываются одинаково |
| CTA унифицирован | Везде один и тот же next step |
| Неполные данные не ломают карточку | Нет `NaN`, пустых процентов и исчезающих блоков |
| Home и `/animals` говорят одним языком | Карточка ощущается одной сущностью, а не разными версиями |
| Тесты закрепляют contract | Есть helper tests и smoke coverage |

## Immediate Next Action

Следующий практический шаг после этой очереди — **сделать inventory всех карточечных surface-слоёв и зафиксировать canonical card contract до начала рефакторинга**. Иными словами, начинать нужно не с красивого общего компонента, а с определения: какие поля, статусы, подписи и CTA обязаны совпадать между Home и `/animals` [1] [3] [4].
